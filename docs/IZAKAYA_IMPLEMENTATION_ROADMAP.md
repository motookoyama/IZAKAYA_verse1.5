# IZAKAYA verse 実装経緯ロードマップ

## 0. この文書の役割

この文書は、`IZAKAYA verse` のここまでの実装経緯を大まかに固定し、
新しい方法論や生成思想を組み込む際の基準線にするためのロードマップである。

目的は、細かな履歴を完全再現することではなく、
「どの層の整備が先にあり、何が後から乗ってきたか」を短く共有することにある。

## 1. 全体像

`IZAKAYA verse` は、単一機能の開発ではなく、以下の層が累積してできている。

1. 世界観と母体構想
2. ローカル実装基盤
3. リージョンとカードのコンテンツ層
4. 公開導線としての UI 層
5. 運用整備と自動化層
6. 新しい生成方法論の追加層

構造的な難しさは、後ろの層を足すたびに、前の層との整合調整が必要になる点にある。

## 2. フェーズ別の流れ

### Phase 0: 母体構想の形成

- オンライン ChatGPT プラットフォーム側に母体プロジェクトが存在
- 世界観、価値観、IZAKAYA の大方針はまず母体側で育った
- ローカル repo は、その派生実装拠点として位置づいた

この段階では「何を作るか」の核が重視され、
実装よりもコンセプトと構想整理が中心だった。

### Phase 1: ローカル実装基盤の成立

- `IZAKAYA_verse1.5` リポジトリがローカル実装基盤として運用開始
- Vue + Vite ベースの画面実装と公開導線の骨格が整備された
- `IZAKAYA 1.6` という運用ラベルが現在フェーズとして使われるようになった

この段階では「動く場所を作る」ことが主眼であり、
思想や素材の多さに対して、実装側の器を先に作る流れだった。

### Phase 2: コンテンツ資産の蓄積

- `src/data/regions/` にリージョン群が蓄積
- `src/data/v2cards/` にキャラクターカード群が蓄積
- 世界観、人物、場の断片がデータ資産として増えていった

この段階で、プロジェクトは単なる UI から
「コンテンツ資産を抱えるアーカイブ」へ変質した。

### Phase 3: 公開導線の再編

- Home, Region, Library, Chat を軸にした導線が重要になった
- Showcase 5 リージョンを中核公開セットとして整理する発想が出た
- `iz_help_nexus` を案内拠点に据える方向が見えた

この段階では、「何があるか」より「どう見せるか」が主要課題になった。

### Phase 4: 運用整備の必要化

- 資産増加により命名、配置、優先順位、更新記録の問題が表面化
- 総合スレ、運用メモ、管理文書の必要性が高まった
- ローカル変更を母体へどう返すかも論点になった

この段階から、コンテンツ開発と同じくらい、
運用整備そのものが実装課題として扱われるようになった。

### Phase 5: 生成方法論の導入

- YOMOYA のような新しい生成手法が企画に入ってきた
- 三題噺起源、seed 分類、ドラマツルギー合成規則などが整理され始めた
- 単発生成ではなく、再利用・転用・評価を前提にした生成思想へ進んだ

この段階で、プロジェクトは
「既存コンテンツを載せる器」から
「新しいコンテンツ生成法を内蔵する基盤」へ拡張し始めた。

## 3. 現在の構造的問題

新手法を導入するたびに、以下の問題が起きやすくなっている。

1. 既存リージョンやカードとの接続点が曖昧になる
2. ドキュメントが増える一方で、優先順位が見えにくくなる
3. 母体構想、ローカル実装、運用文書の境界が曖昧になる
4. 新しいアイディアが UI 実装へどう反映されるかが即座に決まらない

つまり、課題は「発想不足」ではなく、
発想をどの層へ差し込むかの調整コストが上がっていることにある。

## 4. 今後の導入ルール

今後、新しい方法論や生成思想を加える場合は、まず次のどこへ属するかを決める。

1. `content`
   リージョン、カード、設定、物語種
2. `implementation`
   ページ、導線、表示、データ接続
3. `operations`
   管理、命名、保存、評価、母体同期
4. `methodology`
   YOMOYA のような生成技法、評価規則、ドラマツルギー規則

この分類を通さずに足すと、後で全体調整コストが跳ね上がる。

## 5. 現在地

現在の `IZAKAYA verse` は、以下の地点にいるとみなす。

- 世界観資産はかなり蓄積している
- 公開導線は再編途中である
- 運用整備はようやく文書化が始まった段階である
- 生成方法論は導入初期であり、既存資産との接続設計がこれから必要である

つまり、いま必要なのは新規案を増やすことそのものではなく、
既存資産、公開導線、運用整備、生成方法論を接続する中間設計である。

## 6. 当面のロードマップ

1. 既存コンテンツ資産の中核を固定する
   Showcase 5 リージョン、主要カード群、主要ページの役割を固める。
2. 運用文書を索引化する
   どの文書が何を担当するかを整理する。
3. YOMOYA などの新手法の差し込み先を決める
   `plot_seed`、`character_seed`、`region_seed` をどこへ接続するかを定義する。
4. 母体プロジェクトへの還元単位を揃える
   ローカル整理結果を母体へ戻しやすい文章単位にまとめる。
5. UI 反映計画を作る
   新しい生成法を、リージョン、キャンペーン、ライブラリ、イベント導線へどう見せるかを決める。

## 7. 固定メモ

- このロードマップは厳密な年表ではなく、構造理解のための簡易版である
- 新しい方法論を追加する前に、まずこの文書のどのフェーズに影響するかを確認する
- 母体側の大方針が更新された場合、この文書も合わせて更新する

## 8. 2026-05-29 公開再開ロードマップ

目的は、整備済みの Narrative Forge / Preview Server / V2Card / QR 転生コード / ナレッジサイクル基盤を使い、リージョンサービスを順次公開しながら、IZAKAYA verse の本格サービス再開へ進めることである。

### 8.1 主線

1. リージョンサービスを順次公開する
   公開可能なリージョンから、パブリック公開とステルス公開を分けて進める。1 回の push では必要差分だけを選別し、V2 カード体系の大規模整理とは混ぜない。
2. 連動するプロモ活動を開始する
   SNS のキャラクター投稿、QR 転生コード / Region Portal QR 配布、代表画像、短文紹介、導線をセットで扱う。
3. Xe コンテンツ登録へ進める
   公開済みまたはステルス公開済みのリージョンから Xe 登録候補を選び、体験説明、QR、V2 カード連携を整える。
4. 新作リージョンと新キャラクターカードを生産登録する
   Narrative Forge Pro と V2Card 運用を使い、試験成果物と本採用成果物を混ぜずに登録する。良いカードは公式ライブラリー登録候補とする。
5. 本格サービス再開を宣言する
   公開リージョン、プロモ導線、Xe 登録、チャット体験、QR 導線が一定数そろった段階で、IZAKAYA verse の本格サービス再開として告知する。

### 8.2 予備線

- IZAKAYA 1.5 基本チャット bot サービスをブラッシュアップする
- ライブラリーの表示と編集 UI を調整する
  例: 画面が大きすぎる箇所を縮小し、カード確認と編集を作業用サイズへ寄せる。
- ブラッシュアップに伴うテストシミュレーションを行う
  サービスが詰まっていないか、公開導線、チャット導線、ライブラリー導線を確認する。
- 旧 V2 カードと新 V2 カードの扱いを分離する
  リージョン公開 push を優先し、旧カード削除や ID 移行は別フェーズで安全に扱う。

### 8.3 完了目安

- 少なくとも 3 本の公開リージョンが告知可能な状態になる
- ステルス公開リージョンの確認導線が機能する
- SNS / QR / Xe のいずれかの外部導線が実際に通る
- V2 カードとチャット確認が、公開判断の前に最低 1 回通る
- GitHub へ push する差分が、公開パッケージとして説明可能な単位に分かれている
