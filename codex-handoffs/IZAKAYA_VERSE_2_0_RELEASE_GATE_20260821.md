# IZAKAYA Verse 2.0 静的公開・商業ゲート修正指示

制定日: 2026-08-21  
発行者: オーナー承認済み（運営部）  
対象: IZAKAYA Verse 2.0 開発班／検証班  
状態: **静的公開修正をGO。商業ゲート本番はHOLD。**

## 0. 一行の目的

`IZAKAYA Verse 2.0` を、利用者自身のAIで安全に遊び始められる**静的ガイド／Direct BYOK公開面**として完成させる。運営が推論費・画像生成費・ユーザーAPIキーを引き受けるサービスにはしない。

商業ゲート（アカウント、ポイント、PayPal照合、期限アクセス）は別の完成条件を持つ。静的公開のために課金を仮接続したり、旧購入導線を残したりしない。

## 1. 役割と権限

| 役割 | 担当 | 権限・責務 |

| 開発班／Implementer | 本指示のコード修正とテスト | 下記の静的公開必須項目を満たす。範囲外の商業実装へ拡張しない。 |

## 2. 今回GOする範囲

- 版名・画面上の表記を `IZAKAYA Verse 2.0` に統一する。
- トップ、リージョン一覧／詳細、共通ガイド、V2 Build Knowhow、メタチューバー、Narrative Forge案内、Mind Sync案内、Library、Direct BYOKを静的公開候補として完成させる。
- Direct BYOKで、選んだ公式V2カードの**実際の人物情報**を含む、ユーザー自身のAIへ貼り付けるプロンプトを作れるようにする。
- 初心者には Gemini を最初の選択肢として案内してよい。ただし無料・出力品質・各社の継続利用条件は保証しない。APIキー・推論・画像生成・支払は常に利用者側で行う。
- 2.0の初期公開は、閲覧、配布、BYOKガイド、ローカル保存を中心とする。アカウント作成・ポイント購入・利用権発行を公開条件にしない。

## 3. 静的公開の必須修正（全件必須）

### S-01: 実PayPal導線をPRELAUNCH面から除去する

- `PayPalで購入`、`支援する`、実PayPal URL、PayPal QR、または「決済後は管理側で残高に反映」と読める文言を、Verse 2.0の静的公開面から削除または確実に無効化する。
- 隠しメニュー、折り畳み、古い詳細画面、モバイル表示も対象にする。
- 代わりに必要なら「ポイント販売・アカウント利用は準備中。公開ガイドは無料で閲覧可能」とだけ表示する。
- **禁止:** テスト目的を含め、実PayPal画面を開くリンクを残すこと。手動で残高反映する暫定販売も開始しない。

### S-02: V2カード正規化を直し、実内容をDirect BYOKへ渡す

- `izakaya_v2.card` 形式を、既存形式と同じ正規化経路で読めるようにする。
- 少なくとも `name`、`summary`、`personaPrompt`、`first_mes`（存在する場合）をDirect BYOKの生成プロンプトへ入れる。
- UIの選択スロットを変えたとき、生成プロンプトが該当カードの情報へ即時更新されるようにする。
- `アストライア・リライト` など実在する新V2 JSONをfixtureとして、名前だけでなく人格文または概要文、初回メッセージがプロンプトに存在する回帰テストを追加する。
- **禁止:** 空の概要を「カード体験」と表示すること。カード形式未対応を黙って名前だけへ劣化させること。

### S-03: 初回配信容量を縮小する

- V2カード全件の原JSON、base64埋込み画像、高解像度画像を初期JavaScriptへ eager import しない。
- 一覧には軽量な明示メタデータ（ID、名前、リージョン、短い説明、最適化済みサムネイルURL程度）を使う。
- 詳細なV2本文は、カードを選択・詳細表示した時点で遅延読込するか、初期公開面で不要なら読み込まない。
- ビルド後に初期ルートのJS容量、最大チャンク、総転送対象を記録する。Vite警告を残したまま「モバイル対応済み」としない。
- 数値目標は実データで決めるが、前回計測の初期JS約16.4MB・出力約167MBをそのまま公開しないことを最低条件とする。

### S-04: 版名と公開状態を矛盾させない

- 表記は `IZAKAYA Verse 2.0` とする。物理フォルダ名・既存URL・1.6の履歴は変更しない。
- `PRELAUNCH` は「機能や販売が開始済み」を意味しない文脈で使用する。
- 旧BFF Liteの7日TTL、旧QR試作、旧PayPal説明を2.0のサービス仕様として表示しない。
- 公式サイトのトップから到達する全主要画面で、運営はAI推論・画像生成・APIキー保管を行わない方針を、過不足なく一貫して案内する。

### S-05: 世界・ビジュアルを先に見せ、ヘルプは待機導線にする

- 来訪直後の優先順位は、世界／リージョン／キャラクターなどのビジュアル体験、試遊、ライブラリー、遊び方、ヘルプの順とする。
- 「遊び方」「ヘルプ」「FAQ」「制作検品の状態」は、世界へ入る前の大きな操作盤として置かない。困ったときの小さな補助リンク、または閉じた詳細として後方に置く。
- リージョン一覧は、説明・内部レビュー表示より先に、選べるリージョンカードを提示する。ヘルプ用リージョンも、通常の世界の後ろへ配置する。
- 内部の画像判定、再実行状態、未確定作業などの開発用語を来訪者向けの面へ出さない。
- この要件はUIの着脱式スキンに限る。商業ゲート、カード実データ、保存方式、バックエンドの仕様を変更しない。

## 4. 静的公開の検証・受入条件

開発班は、ソース確認だけで完了報告をしてはならない。次をすべて提出する。

1. `npm run test:region-protocol-gate` が成功すること。
2. `vue-tsc` と通常ビルドが成功すること。
3. Pages向けは、既存 `docs/` を上書きしない dry-run 出力でまず確認すること。公開用 `docs/` の更新やGitHub Pages公開は、オーナーの別承認後に行うこと。
4. ローカルブラウザで、トップ、リージョン一覧、少なくとも一つのリージョン詳細、共通ガイド、V2 Build Knowhow、メタチューバー、Narrative Forge、Mind Sync、Library、Direct BYOKを確認すること。
5. Direct BYOKで実在V2カードを選び、生成プロンプト内にカード名と人格／概要／初回メッセージの実データがある証跡を残すこと。
6. デスクトップと幅390px程度のモバイル表示で、ナビゲーション、カード選択、プロンプト更新、外部ガイドリンクを確認すること。
7. 全主要ルートで、実PayPal URL、購入・支援ボタン、決済後の手動残高反映文言が存在しないことを、画面とソース検索の両方で確認すること。
8. 初期読込容量の測定値と、S-03で採った分割／遅延読込方針を報告すること。
9. ブラウザconsoleのエラー、リンク切れ、画像表示失敗を、確認したルートごとに報告すること。

## 5. 商業ゲート: 今回は本番HOLD、次フェーズの必須条件

`services/region-protocol-gate` のPhase A（ローカル・副作用なし）は進捗として受理する。ただし、これは販売開始の承認ではない。

Sandboxへ進む前に、次を実装・検証する。

- サーバー側で注文を事前作成し、アカウントID、商品、期待額、通貨、受取先、注文IDを固定する。
- PayPalの検証結果を、上記の期待値と照合してからだけ台帳へ反映する。webhookの `verified: true` やcapture ID単独を、ポイント付与の根拠にしない。
- 認証済み主体だけが自分の残高・利用権・申請を読めること。
- Firestoreでは、ポイント消費と利用権発行を単一トランザクションにし、決済イベント／capture IDを永続的に重複排除する。
- Sandboxで成功、取消、金額不一致、通貨不一致、受取先不一致、重複webhook、再送、期限切れ、残高不足を証跡付きで確認する。
- GCPプロジェクト作成、API有効化、Cloud Run／Firestore作成、PayPal本番接続、実販売は、オーナーの個別承認まで実行しない。

### 5-A. 2026-08-23 Sandbox基盤スモーク（承認済み・販売開始ではない）

オーナーの個別承認により、商業ゲートの**基盤接続だけ**をSandboxで検査した。

- Firebase連携済みのSandboxプロジェクトに、東京リージョンの空Firestoreを作成した。
- `izakaya-commercial-gate-sandbox` は `/health` の読取接続だけを行う非公開Cloud Runサービスである。常駐ゼロ、最大1インスタンス、同時実行1、タイムアウト10秒に固定した。
- 専用実行者にはFirestoreの読取権限だけを与えた。ユーザー情報、ポイント、利用権、決済、秘密情報、AI推論、画像生成の書込み・処理は未実装かつ無効である。
- 認証付きの `/health` 実行で、Cloud RunからFirestoreへの読取接続が成功した。公開アクセス許可は付けていない。

これはSandboxインフラの接続証跡であり、PayPal Sandbox連携、Firestore台帳アダプタ、アカウント認証、ポイント発行、実販売、本番IPN変更の承認を意味しない。それらは本節の必須条件を実装・検証してから別途判断する。

### 5-B. 公開後の軽量化チェック（未着手・判断待ち）

Firebase向け静的ビルドは2026-08-23時点で約131MB（素材込み）、初期JavaScriptは約319KBである。現時点では公開面の内容・見た目を固定しており、素材を削除または置換していない。

次の公開後改善として、以下を測定したうえでオーナーへ選択肢を提示する。

- 初回表示・リージョン詳細・V2カード詳細ごとの実転送量と待機時間
- 高解像度画像の配信サイズ、サムネイル分離、AVIF/WebP化の効果
- V2原本JSONを初回公開物から分離し、必要時だけ取得する方法
- 見た目、既存URL、カード原本を壊さない段階的な削減計画

この項目は「直ちに削る」指示ではない。公開内容の確認後、効果・手間・画質の比較を見てから個別にGOする。

## 6. 今回の非目標・禁止事項

- BFF Liteの既存未コミット変更を削除・巻戻し・上書きしない。
- AI推論プロキシ、ホスト型チャット、画像生成代行、ユーザーAPIキー保管を追加しない。
- Google Cloud／AWS／Renderの課金設定、デプロイ、API有効化、本番DB作成を行わない。
- PayPal本番決済、ポイント販売、返金実行、SNS技術告知を行わない。
- V2原本、会話ログ、高解像度画像を住民カタログや一般DBへ収集しない。
- Clone V2、公開住民カタログの受理、リアルタイムMMOを、2.0静的公開の必須機能にしない。
